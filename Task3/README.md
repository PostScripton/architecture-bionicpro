# Задание 3. Снижение нагрузки на базу данных

## Архитектурное решение

<img src="/images/tasks/Task3/s3_cdn_caching.svg" alt="Кеширование отчётов через S3 и CDN"/>

Готовые отчёты сохраняются в объектное хранилище S3 (Minio) и раздаются через Nginx, настроенный как reverse proxy с кешированием статических файлов (эмуляция CDN). `reports-api` при запросе сначала проверяет наличие отчёта в S3 и, если он уже есть, сразу отдаёт ссылку на CDN, не обращаясь к ClickHouse. Если отчёта ещё нет, сервис читает готовую строку витрины, кладёт JSON в S3 и только после этого отдаёт CDN-ссылку.

## Структура хранения в S3

Ключ объекта - `<username>/<report_date>.json`, бакет `reports`. Такая структура даёт:

- быстрый доступ - объект однозначно адресуется по пользователю и дате, без листинга бакета и без полнотекстового поиска;
- иммутабельность - витрина в ClickHouse (`reports.user_report_mart`) наполняется Airflow один раз в сутки за завершённые сутки (см. [Задание 2](../Task2)), поэтому отчёт за конкретную дату не меняется задним числом и объект по этому ключу можно кешировать сколь угодно долго без инвалидации по TTL.

`reports-api` вычисляет ожидаемую дату отчёта (`today - 1 день`) на основе расписания DAG `crm_telemetry_reports_etl` (`0 3 * * *`, обрабатывает предыдущие сутки), не обращаясь к ClickHouse. Это значит, что при повторных запросах пользователя сервис делает только `HEAD` в S3 - ClickHouse запрашивается исключительно при первом запросе отчёта за новую дату, когда объекта в S3 ещё нет.

## Механизм обновления кеша в CDN

Поскольку объект в S3 иммутабелен (новый отчёт - это всегда новый ключ с новой датой), классическая инвалидация не нужна:

- Nginx кеширует ответы `200` на 30 дней (`proxy_cache_valid 200 30d`) - старый контент по тому же URL никогда не станет невалидным, потому что URL и есть версия отчёта.
- Ответы `404` (объект ещё не сформирован) кешируются всего на 10 секунд, чтобы не создавать лишнюю нагрузку на Minio, пока `reports-api` не положит туда отчёт, но и не задерживать раздачу свежесозданного объекта.
- `proxy_cache_use_stale` отдаёт последнюю закешированную копию, если Minio временно недоступен.

## Компоненты

- [`reports-api/main.py`](../reports-api/main.py) - логика `HEAD` в S3 перед обращением к ClickHouse, генерация и `PUT` отчёта при промахе кеша, формирование CDN-ссылки. Конфигурация S3 и CDN вынесена в [`reports-api/config.py`](../reports-api/config.py) (`S3_ENDPOINT_URL`, `S3_BUCKET`, `CDN_BASE_URL` и т.д.).
- [`nginx/nginx.conf`](../nginx/nginx.conf) - reverse proxy перед Minio с `proxy_cache_path` и правилами кеширования, отдельным health-check эндпоинтом и CORS-заголовками для прямого запроса из браузера.
- [`docker-compose.yaml`](../docker-compose.yaml) - сервисы `minio` (S3 API и консоль), `minio-init` (разовое создание бакета `reports` и политики анонимного чтения через `mc`) и `nginx-cdn` (сам CDN, порт 8082).
- [`frontend/src/components/ReportPage.tsx`](../frontend/src/components/ReportPage.tsx) - после получения `report_url` от `reports-api` фронтенд отдельным запросом читает содержимое отчёта напрямую с CDN, не нагружая `reports-api` и `bionicpro-auth`.

`bionicpro-auth` не менялся - он по-прежнему прозрачно проксирует `/reports`, добавляя туда access-токен.

## Проверка

Стек поднят через `docker-compose up` (`minio`, `minio-init`, `nginx-cdn`, `reports-api` и их зависимости):

- `minio-init` создаёт бакет `reports` и открывает анонимное чтение (`mc anonymous set download`) - без этого Nginx не смог бы отдавать объекты без подписи каждого запроса.
- Первый `GET /reports` с валидным токеном для пользователя, у которого уже есть строка в витрине за вчерашний день: `reports-api` не находит объект в S3, читает витрину, кладёт JSON в S3 и возвращает `{"status": "ready", "report_url": "http://localhost:8082/reports/<username>/<date>.json"}`.
- Запрос этого `report_url` напрямую отдаёт `X-Cache-Status: MISS` на первый заход и `HIT` на повторный - Nginx отдаёт закешированную копию, не обращаясь к Minio.
- Повторный `GET /reports` в `reports-api` для того же пользователя выполняет только `HEAD` в S3 и сразу возвращает ту же ссылку - обращения к ClickHouse не происходит.
- Пользователь без данных за вчерашний день по-прежнему получает `202 pending`, без токена - `401`.
